# MISSION.md 格式

`MISSION.md` 放在工作区根目录，发布于 `/MISSION`。它记录用户学习这个主题的**原因**。所有教学决策（下一课教什么、推哪些资源、设计什么练习）都要能追溯到这里。

## 模板

```md
# Mission: {主题}

## 为什么

{1-3 句。用户在追的具体现实目标。学会之后，他的工作或生活会有什么不同？拒绝「想了解 X」这类抽象说法，追问背后的结果。}

## 达成时是什么样

- {一个具体、可观察的能力}
- {另一个具体能力}
- {…}

## 约束

- {时间、预算、已有承诺、学习偏好——任何限制路径选择的东西}

## 不做什么

- {用户明确暂时不追的邻近主题，用来保护最近发展区}
```

## 规则

- **一个工作区一个 mission。** 两件不相关的事是两个工作区。
- **具体优于抽象。** 「10 月前跑完半马」优于「变得更健康」；「给团队上线一个 Rust CLI」优于「学 Rust」。
- **含糊就顶回去。** 如果用户说不清为什么，先访谈再动笔。一个烂 mission 比没有 mission 更糟。
- **现实变了就改。** 目标改变时更新本文件并补一条 learning record，不要让过期的 mission 继续指挥后面的课。
- **保持短。** 超过一屏，它就从指南针变成了计划书。

## 多主题时

如果用户想学的东西和当前 mission 无关，不要塞进同一个站点：新建工作区，并在两边的 `NOTES.md` 里互相记一句「另一门课在哪」。这样不会混，也不会丢。

## 在站点里

课程用 `[目标](/MISSION)` 链接到这里。这一页会被发布，所以不要写读者看不懂的内部笔记：没有待办、没有 agent 草稿。那些属于 `NOTES.md`（已被构建排除）。
